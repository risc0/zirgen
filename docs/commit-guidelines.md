# Commit Message Guidelines

This document provides detailed guidelines for writing commit messages in the Zirgen repository.

## Overview

All commits must follow the format: `ZIR-XXX: Description`

This standardized format provides:
- **Traceability**: Every commit links to a specific task or issue
- **Consistency**: Easy to scan and understand commit history
- **Automation**: Tools can parse and process commits reliably
- **Clarity**: Developers immediately understand what issue a commit addresses

## Format Specification

### Basic Structure

```
ZIR-<number>: <description>

[optional body]

[optional trailers]
```

### Components

#### 1. Issue Prefix (Required)

- Format: `ZIR-` followed by one or more digits
- The number corresponds to the issue or task being addressed
- Examples: `ZIR-1`, `ZIR-123`, `ZIR-9999`

#### 2. Separator (Required)

- Must be a colon followed by a space: `: `
- No other separators are accepted

#### 3. Description (Required)

- Brief summary of the change
- Use imperative mood ("Add feature" not "Added feature" or "Adds feature")
- Start with a capital letter
- No period at the end
- Aim for 50-72 characters
- Be specific and descriptive

#### 4. Body (Optional)

- Separate from subject with a blank line
- Explain what and why, not how
- Wrap at 72 characters
- Can include multiple paragraphs
- Use bullet points for multiple items

#### 5. Trailers (Optional)

- Special metadata in `Key: Value` format
- Common trailers:
  - `Co-Authored-By: Name <email>`
  - `Signed-off-by: Name <email>`
  - `Nightshift-Task: task-id`
  - `Nightshift-Ref: url`

## Examples

### Simple Commit

```
ZIR-123: Add support for new RISC-V instruction
```

### Commit with Body

```
ZIR-456: Fix memory leak in witness generation

The witness generator was not properly releasing memory after
processing large circuits. This commit adds proper cleanup in
the destructor and ensures all allocated resources are freed.
```

### Commit with Multiple Details

```
ZIR-789: Optimize polynomial evaluation in prover

Improves performance by 40% for large circuits through:
- Caching repeated polynomial evaluations
- Using SIMD instructions for batch operations
- Reducing memory allocations in hot path

This addresses the performance regression introduced in ZIR-750.
```

### Commit with Trailers

```
ZIR-321: Add comprehensive test suite for recursion

Co-Authored-By: Jane Developer <jane@example.com>
Nightshift-Task: test-coverage
```

## Writing Good Descriptions

### Do

- **Be specific**: "Fix off-by-one error in memory access" not "Fix bug"
- **Use imperative mood**: "Add feature" not "Added feature"
- **Focus on what changed**: "Remove deprecated API endpoint"
- **Keep it concise**: Aim for under 72 characters
- **Capitalize**: Start with a capital letter

### Don't

- **Be vague**: "Update code" or "Fix things"
- **Use past tense**: "Added feature" or "Fixed bug"
- **Include technical details**: Save for the body
- **End with period**: The subject line is a title, not a sentence
- **Reference code specifics**: "Fix bug in src/foo.rs:123" → use body

## Validation

### Automated Checks

The repository includes a git commit-msg hook that validates every commit message. The hook checks:

1. Format matches `ZIR-<number>: <description>`
2. Issue number contains at least one digit
3. Colon and space are present after the issue number
4. Description is not empty

### Exceptions

These commit types bypass validation:
- **Merge commits**: Automatically generated by git
- **Revert commits**: Created by `git revert`
- **Empty commits**: Commits with no message or only comments

### Testing Your Message

Before committing, you can test your message manually:

```bash
# Test a message
echo "ZIR-123: Add new feature" | .git/hooks/commit-msg /dev/stdin

# If valid, no output. If invalid, you'll see an error message.
```

## Troubleshooting

### Hook Not Running

If the commit-msg hook isn't validating your commits:

```bash
# Check if hook exists
ls -la .git/hooks/commit-msg

# Make it executable
chmod +x .git/hooks/commit-msg

# Verify it runs
.git/hooks/commit-msg .git/COMMIT_EDITMSG
```

### Template Not Showing

If you don't see the template when committing:

```bash
# Check current setting
git config commit.template

# Set it manually
git config commit.template .git/commit-msg-template
```

### Bypassing the Hook (Not Recommended)

In rare cases where you need to bypass the hook:

```bash
git commit --no-verify -m "Emergency fix"
```

**Note**: This should only be used in exceptional circumstances and requires justification in code review.

## Best Practices

1. **Create issues first**: Every commit should reference an existing issue
2. **Atomic commits**: Each commit should address one logical change
3. **Review before committing**: Read your message as if you're seeing the commit for the first time
4. **Use the body**: For non-trivial changes, explain the reasoning
5. **Link related work**: Mention related issues in the body (e.g., "Builds on ZIR-100")
6. **Consider the reader**: Someone reading `git log` should understand what happened

## Integration with Development Workflow

### Before Committing

1. Run tests: `cargo test`
2. Format code: `cargo fmt`
3. Check lints: `cargo clippy`
4. Review changes: `git diff --staged`
5. Write clear commit message following this format

### During Code Review

Reviewers should check that:
- Commit messages follow the format
- Issue numbers are valid
- Descriptions accurately reflect changes
- Complex changes include body text with rationale

### After Merging

The standardized format enables:
- Generating changelogs automatically
- Tracking issue completion
- Understanding project history
- Identifying changes related to specific features
